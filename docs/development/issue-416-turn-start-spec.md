# 公开 TurnStart 幂等准入与有界恢复 SPEC

状态：待评审的实施规格；不表示功能已实现。需求来源：[Issue #416](https://github.com/Plantcore-AI/Iteron/issues/416)。

## Problem Statement

使用公开产品控制接口的客户端启动一个产品 Turn 后，可能在收到回复前断线，或遇到服务进程重启。当前 `TurnStart` 只携带线程 ID 和文本；服务端返回的 submission ID 是本次入队的关联 ID，`control_queued_v1` 也只表示入队。客户端无法判断原请求是否已持久准入，盲目重发可能启动第二个 Turn，再次调用模型、执行工具并计费。现有事件游标重连解决的是事件读取，不解决启动请求的幂等准入。

这里的**产品 Turn**是一个用户可见的工作单元，可包含多次模型调用及工具执行；它不同于记录中的单次模型 `TurnStart`。**TurnStart 请求键**由客户端为一次启动意图生成，重试时保持不变；它不同于控制消息 ID 和服务端生成的 submission ID。

## Solution

公开 `TurnStart` 增加必填的客户端请求键，产品契约升级到 V2。请求键由 UUIDv7 随机身份与原请求摘要组成。客户端在有效窗口内用原键、原线程和原文重试，取得同一个已准入 Turn 的持久身份及当前有证据支持的状态。同键改动线程或请求内容返回冲突，绝不启动第二个 Turn；即使首次请求因容量满而未被服务端记录，也能依据键内摘要检测冲突。首次请求明确未准入时，同键同请求可以再次尝试准入。

服务端在执行 Turn 前持久提交请求键、精确请求摘要、submission／产品 Turn 关联身份及权威准入回执；并发请求经过同一个持久准入权威。终态也以持久证据确认。回复丢失、断线和重启后，服务端可通过重试原 `TurnStart` 恢复已知结果；若准入本身无法判明，返回“准入未知”；若只能证明准入而不能证明终态，返回“结果未知”。两者都不触发自动重演。队列回执始终不代表持久准入。

## User Stories

1. 作为公开产品控制客户端，我希望为一次 TurnStart 生成稳定请求键，以便在网络失败后安全重试。
2. 作为客户端，我希望回复丢失后用原键和原请求找回原 Turn，以便避免重复执行。
3. 作为客户端，我希望顺序重试取得相同的准入身份，以便关联同一次工作。
4. 作为客户端，我希望并发重试也只准入一个 Turn，以便不会发生重复模型调用、工具执行或计费。
5. 作为客户端，我希望重试时得到当前有证据支持的状态，以便知道原 Turn 的进展。
6. 作为客户端，我希望用现有线程快照和事件读取获取正文、错误详情，以便重试回执保持简短。
7. 作为客户端，我希望同键但不同文本或线程被明确拒绝，以便发现错误复用请求键。
8. 作为客户端，我希望已明确拒绝且从未准入的请求能在有效期内重试，以便在容量恢复后继续尝试。
9. 作为客户端，我希望已准入但执行失败的请求仍返回原 Turn 状态，以便不会无意重新执行副作用。
10. 作为客户端，我希望需要重新执行时使用新键，以便将两次意图区分开。
11. 作为客户端，我希望过期键被明确拒绝，以便不会把旧请求误当作新请求。
12. 作为客户端，我希望客户端时钟过快得到明确拒绝，以便识别时钟配置问题。
13. 作为客户端，我希望断线或重启后找回可证明的准入及终态，以便不依赖易丢失的队列回执。
14. 作为客户端，我希望无法证明终态时看到“结果未知”，以便不会把未知误判为成功、失败或未执行。
15. 作为运维人员，我希望记录容量和恢复时间均有上界，以便高峰或故障不会造成无限资源占用。
16. 作为现有通用 `submit` 客户端，我希望产品契约升级不改变我的请求路径，以便现有通用提交流程继续按原契约运行。
17. 作为维护者，我希望启动、执行、副作用与用量的证据仍遵守现有权威边界，以便重试不能绕过权限或重复记账。

## Implementation Decisions

### 公开契约与判等

- 仅修改公开产品控制 `TurnStart`。它要求 `request_key`、`thread_id`、`text`；`request_key` 的规范形式为 `UUIDv7:sha256-hex`，其中 UUIDv7 是每次新启动意图都重新生成的随机身份，后缀是小写 64 位十六进制摘要，完整键长 101 个 ASCII 字符。线程与文本使用现有边界校验。相同完整键在同一持久准入权威覆盖的所有线程中唯一。
- 产品契约版本从 V1 升至 V2；不提供旧格式 `TurnStart` 的兼容路径。握手版本不匹配及缺少、畸形或过期请求键均明确拒绝。通用提交协议版本不因本变更升级。
- 对请求身份的比较使用线程 ID 与原始 UTF-8 文本字节，不做 trim、Unicode 归一化或其他隐式变换。摘要为 SHA-256 对 `UUIDv7 原始 16 字节 || thread_id 字节长度 || thread_id 原始字节 || text 字节长度 || text 原始字节` 的结果；两个长度均用无符号 64 位大端整数编码。摘要覆盖所有影响启动语义的请求字段，UUIDv7 随机量也使相同文本的不同启动意图产生不同摘要。实现不能仅凭截断文本比较。持久记录只存摘要，不重复保存完整输出。
- 服务端解析完整键后，先依据请求的原始线程和文本重算键内摘要；不匹配一律返回 `request_conflict`，不准入、不排队，包括容量满、队列满、记录已清理或键已过期的情况。只有摘要匹配才检查键的有效期、请求有效性、持久记录和准入容量。容量满等明确拒绝且未登记时，同键**同请求**仍可在有效期内重试；同键改内容依然冲突。服务端不得在不确定登记或准入是否完成时声称此前未准入。
- 服务端生成的 submission ID 仍用于提交关联；它不能代替客户端请求键，也不能单凭入队回执证明准入。首次回执可表示等待准入，只有持久准入回执才能称为“已准入”。重试保持原准入身份不变，状态可随证据更新，无需逐字复现首次回执。
- 重试 `TurnStart` 是唯一的按键恢复操作，不增设查询命令。重试回执只返回准入身份、当前状态及有限错误码；正文与错误详情继续通过线程快照和事件读取获得。

V2 回执采用以下封闭字段和状态集合。状态类回执带 `type=turn_start_receipt_v2`、`contract_version=2`、`request_key`、`thread_id`、`state`、`submission_id`、`run_id`、`turn_id`、`window_closed`；三个身份字段在尚未**证明**持久准入时为 `null`，准入得到证明后固定且非空。`window_closed` 表示 30 分钟按键恢复窗口已经结束，不改变已知准入事实。`run_id` 与产品 `turn_id` 合起来是跨重启稳定的 Turn 身份，submission ID 只是关联字段。拒绝类回执带 `type=turn_start_refused_v2`、版本、请求键、`reason_code` 和 `definitely_unregistered`，不携带准入身份；非法键因无法安全回显可为 `null`。仅当持久权威证明键未登记且请求未准入时，`definitely_unregistered` 才为 `true`；`false` 不断言此前是否准入。不得把拒绝类回执解释为 Turn 终态。

| `state` | 成立所需证据 | 允许的后续结果 |
|---|---|---|
| `pending` | 持久键记录存在，尚无持久准入；当前进程仍能确认该尝试在队列中 | `admitted`、明确未准入的拒绝 |
| `admitted` | 键、摘要、submission／产品 Turn 身份及准入事实已原子持久提交 | 活动进程中的 `running`；持久终态；重启后证据不足时 `unknown` |
| `running` | 已持久准入，且当前活动进程的运行时证实该 Turn 正在执行 | 持久终态；失去活动进程证据后 `unknown` |
| `completed`、`interrupted`、`drained`、`budget_exhausted`、`stuck`、`failed` | 对应产品 Turn 的完整终态已持久确认 | 原终态保持不变 |
| `unknown` | 能证明已准入，不能证明当前运行或完整终态 | 后续若发现可靠持久终态，可更新为该终态；绝不触发执行 |
| `admission_unknown` | 持久提交或重开时无法可靠判断键是否已准入；不携带未经证明的 submission／Turn 身份 | 同键重试只重新读取持久证据，可变为已证实的准入／终态或已证实未准入；在无法判明期间绝不准入、排队或执行 |

拒绝原因至少区分 `request_conflict`、`invalid_request_key`、`request_key_expired`、`request_key_in_future`、`invalid_turn_text`、`thread_unavailable`、`turn_active`、`capacity_full`、`busy`、`rate_limited` 和 `runtime_disconnected`。协议版本不匹配沿用握手拒绝；它发生在 V2 回执之前。只有服务端能证明未准入的拒绝才允许原键重新尝试；其它不确定故障不能伪装成这种拒绝。`rate_limited` 只表示本次请求未处理，不对既往准入作任何断言，也不消耗或释放请求键。

### 持久准入与恢复

- 在同一记录根和租户范围内设置跨线程、跨进程共享的产品准入记录权威，由记录边界持有，并通过跨进程互斥把同键检查、容量检查、同线程活动／未决 Turn 检查与准入持久提交串行化。关键记录包含请求键、请求摘要、线程身份、稳定的 submission／产品 Turn 关联身份、状态和有效期。可以复用现有持久化原语，但不能依赖仅驻留内存的产品投影或仅逐 run 锁定的记录来保证跨线程唯一性。记录清理及压缩必须保持崩溃后可恢复，且不得删除未过期键。
- 准入点须把键、摘要、关联身份与产品 Turn 的权威准入证据作为一个可恢复的持久提交边界。提交并确认持久化成功后，运行时才能开始该 Turn 的模型调用或工具副作用。提交失败不得宣称准入。并发同键请求只能观察同一提交结果。
- 如需在准入前记录键的占用或等待状态，它只代表尚未准入的尝试。服务进程重启后，只有能证明先前从未准入时，才可在原键有效期内再次尝试；不能从已排队、已收到或缺少内存状态推断准入或未准入。若重启后只有未准入键记录而没有活动队列，重试须先核验原请求，再安全地重新尝试准入；不能永远返回无活动来源的 `pending`。
- 如果持久提交的成功与否、记录完整性或重开结果无法判明，返回 `admission_unknown`，不返回 `definitely_unregistered=true`，也不重新排队。客户端可在窗口内用同键同请求重试以重新读取证据；只在权威记录证明未准入后才允许再次尝试准入。若窗口已结束而准入仍无法判明，仍返回 `admission_unknown` 并明确窗口已关闭，绝不因过期或清理而改报“从未准入”。
- 已准入 Turn 的终态必须由与该身份关联的持久证据证明；单次模型调用的 `TurnEnd`、内存中的产品 `TurnEnded` 或一次入队回执均不足以证明整个产品 Turn 的终态。若重启后只有准入证据而无可靠终态，返回显式“未知”；不自动重新排队或运行。运行中状态仅在当前活动进程可证实时返回，不能把崩溃前的运行中状态当成重启后的实时状态。
- 同键、同请求的重复调用优先查持久准入记录，再检查当前是否有活动 Turn；否则重试会被误判为新的 `turn_active` 冲突。不同键遇到活动或终态未明的同线程 Turn 时拒绝新准入；同线程判定与新准入在同一持久权威的互斥边界内完成。V2 准入必须封闭当前“检查运行状态后才入队”的并发窗口。未决 Turn 的线程占用证据属于会话／Turn 状态，不随 30 分钟请求键记录清理；不能仅因键过期就认定 Turn 已结束。
- 已准入 Turn 无论成功、失败、中断或其他终态，同键均不重新执行。客户端若有意重新执行，必须生成新键；“未知”不能被服务端解释为可安全自动重演。
- 权威准入、运行、终态和现有会话／事件游标的顺序保持一致；只为已持久确认的事实发出成功语义。权限、effect ledger、取消、预算与用量记账仍由既有权威边界处理。

### 有界性与暂定参数

- 请求键有效期固定为键内 UUIDv7 所含生成时间起 **30 分钟**，包括 Turn 尚在运行时。过期后始终禁止新准入，不启动新 Turn，也不声称此前 Turn 已结束或从未准入。同键改内容优先返回 `request_conflict`；同键同内容且准入是否发生仍无法判明时返回 `admission_unknown`、`window_closed=true`；其余同键同内容的过期请求返回 `request_key_expired`。服务端可清理过期记录，但即使记录已清理，仍按键中时间执行上述安全判定。
- 暂允许 UUIDv7 时间比服务端时间最多快 **5 分钟**；更远的未来键拒绝。客户端时钟过慢导致键已过期时也拒绝。窗口与容差均为暂定产品参数，实施前应结合用户可见 Turn 的延迟指标和时钟环境复核。
- 请求键固定为 101 个 ASCII 字符；V2 的线程 ID 与返回的 run ID 各限制为 256 UTF-8 字节，文本继续受现有 1 MiB 上界约束。请求原始帧受现有 headless 输入帧上界约束，V2 单条准入记录序列化后不超过 2 KiB，单条回执序列化后不超过 2 KiB；超限在准入前拒绝。扫描／重开至多访问容量上限 `C` 条未过期键记录，每次 TurnStart 请求及恢复操作最多等待 5 秒，超时明确报错而不推断准入或终态。每个持久权威同一时刻最多一个准入写临界区；服务端对一次准入不做自动重试，也不自动重演已准入 Turn。每个持久权威同时最多处理 32 个 TurnStart 请求，接入速率最多 64 次／秒、突发最多 64 次；超限立即返回 `rate_limited`。已登记键的恢复读取优先于新键准入，不能因为容量满而拒绝已有键的查询。客户端在窗口内可多次同键重试，但每次调用均受上述速率、并发和 5 秒时限约束；限流回复不得隐含未准入或已结束。
- 每个记录根和租户的请求键记录容量 `C=1024`，单条不超过 2 KiB，因此未过期键记录的序列化总量不超过约 2 MiB。容量达到上限时拒绝新键，保留所有未过期记录；已保留键仍可查询原结果。这个暂定值约容纳 30 分钟内平均每 1.8 秒一次新 Turn；一个驻留会话一次仅执行一个产品 Turn，但不同会话可并行，短 Turn 与已结束 Turn 仍占用窗口。实施前按实际部署范围和峰值启动率复核容量，不能直接套用提交队列容量。

### 边界与所有权

- 预期涉及 `protocol-compat`、`cli-host`，以及最终持久化落点对应的 `record-core`／`record-sessions`；实施前由相应人类维护者确认跨边界契约。须保留 `durability-replay`、`frontend-contract`、`boundedness`、`tcb-authority`、`cost-accounting` 不变量。

## Testing Decisions

- 主要验证接缝为公开产品控制／headless 入口到真实驻留 App Server 与可重新打开的持久记录。测试断言客户端可观察的回执、唯一 Turn 身份和模型／工具／用量次数，不绑定内部容器或函数调用次数。优先复用现有产品控制、提交生命周期和记录重开测试设施；无需为每一层分别造协议模拟器。
- 通过这一接缝覆盖：首次准入；顺序和并发同键重试；同键改文本或线程始终冲突，包括明确拒绝且未登记、记录已清理及过期后的情况；同键同请求在明确未准入后重试；不同键同文本；活动 Turn；终态失败后重试；回复丢失、断线和持久提交前后重启；准入已证实但终态未知、准入本身未知及其同键再读；过期键、未来键、容量满、队列满、无效键、版本不匹配；接入速率、突发、并发与 5 秒时限。对模型／工具／用量的重复执行风险给出集成证据。
- 故障注入应覆盖准入持久提交前、提交后而回执前、运行开始前、运行中和终态持久提交前后。每个切点只接受可由证据证明的状态；模拟回执丢失不得直接用内存状态冒充恢复。
- 完成实施前运行格式化、边界检查、all-target check、严格 Clippy 和 all-target tests，并记录精确源码版本及仍不支持的客户端路径。

## Out of Scope

- 不修改 Desktop、Cloud 等当前使用通用 `submit` 的客户端路径，也不将 `TurnStart` 视为 `submit` 的替代品。
- 不增加按键查询命令，不恢复任意工作流或副作用，不实现新的多 Agent 协议。
- 不改变现有事件游标语义，不放宽权限、effect ledger、取消、预算和用量记账保证。

## Further Notes

- 本规格描述待实现契约；不能凭文档或合成 fixture 关闭 Issue #416。
- 键内摘要只证明该完整键绑定的请求内容，不是认证凭证；产品控制仍须经过现有会话身份与权限检查。UUIDv7 的随机部分充当摘要盐值，服务端不得把请求键当作授权依据。
- 30 分钟窗口、5 分钟时钟容差及暂定 1024 条记录容量需要结合业务延迟与部署数据复核。持久权威的实际存储落点与跨边界维护者确认，是实施前尚未完成的事项。
